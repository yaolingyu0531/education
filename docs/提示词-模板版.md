你是一名资深 AI 应用工程师，帮我开发一套「实习反馈受限整理与教学改进辅助」智能体系统。请严格按我给出的技术栈和约束执行，不要自行替换框架、不要引入我没要求的中间件。

【项目背景】

客户：知行职业学院 · 产教协同办公室。试点范围：机电专业 + 5 家企业，预算 12 万元，周期 4 周最小验证；先历史回放、再并行试点，不关停现有人工流程。

客户原话："企业说学生能力不够，老师觉得评价太笼统。希望用 AI 整理实习反馈、发现教学改进需求。"

已确认诊断：客户以为病在"整理慢"，实际病在三处——① 换岗后反馈发给旧导师（f11）；② 企业只写"沟通能力不足"，说不出哪个岗位任务没做好（f10）；③ 建议落不到具体课程（f01）。这三处不修，整理得越快，糊涂账抄得越整齐。因此顺序固定：先修管道（口径 → 岗位任务模板字段 → 换岗重关联 → 双周节拍 → 只读 ID 映射），再装泵（受限 AI 整理）。首期不做自动评价、不做成绩写回。

【系统定位】

一句话：把企业反馈整理成**可追溯到原文、经人确认、且能在"岗位任务→能力→课程"图上连通**的改进建议。系统不产出任何评价结论。

四个部件，各管一件事，不许互相顶替：

| 部件 | 职责 | 不负责 |
| --- | --- | --- |
| Harness | 工具白名单、两级策略、步数与时间预算、全链路 trace | 不决定业务判断，只决定执行边界 |
| 知识库 KB | K1 岗位任务模板 / K2 课程口径 / K3 规则版本；切片检索与引用 | 不判关系；不存个体数据 |
| 知识图谱 KG | 实体关系与多跳查询；可执行性判定；口径断裂量化 | 不做检索；不替代原文引用；不在线写入 |
| 人工闸门 | 确认 / 退回 / 停止 / 签发 / 否决 / 留存处置 | 不手工搬数据 |

单条记录固定 6 步，允许提前终止，不许加第 7 个业务步骤：
`feedback.get → mapping.resolve → task_template.match(+kb.search) → kg.path → evidence.locate → suggestion.draft → review.enqueue`

首期范围（按 M0–M4，对齐业务门）：M0 契约+Harness 骨架+KB/KG schema+Ollama 适配+口径卡（G0）；M1 只读导入+ID 映射+四项校验+K1 入库建初图（G3）；M2 三字段抽取+闸门+图归一审核发布+检索与图评测（G2 前半）；M3 建议草稿+图连通判定 24/30+三引用强制（G2 判定）；M4 指标复算+30 条回放报告+导出（G4）。

明确不做（写了就是错）：成绩/学分写回、任何外部写接口；自动评分/能力定性/学生画像/排名；培养方案变更与通用审批流；通用知识图谱平台（多模态、全网爬取、自由问答、链接预测）；自由对话式入口；课程改进台账；投诉工单；微服务、容器编排、消息队列、Redis、图数据库、向量数据库、LangChain/LangGraph、前端构建链。

模型配置固定（不许散落在代码里）：

```yaml
llm:
  provider: ollama
  base_url: "http://127.0.0.1:11434"
  chat_model: "qwen3:8b"          # Q4_K_M 约 5.2GB
  embed_model: "bge-m3"           # qwen3:8b 不是 embedding 模型，不能替代
  num_ctx: 8192                   # Ollama 默认 4096，长反馈会截断
  num_predict: 1024
  temperature: 0
  top_p: 0.9
  seed: 42
  keep_alive: "30m"
  think: false                    # 抽取任务必须关
  allow_remote: false             # 默认零外发
  model_digest_pin: "<首次 pull 后回填>"
```

三条与 Qwen3-8B 绑定的硬要求（不写清必然返工）：

1. **必须关 thinking**。Qwen3 是混合推理模型，默认先输出"好的，我来分析…"，`format` 约束挡不住思维链文本，JSON 解析必挂。三处同时做：请求体 `think: false`、prompt 末尾追加 `/no_think`、解析层一旦输出不以 `{` 开头就直接判 `E_LLM_INVALID_OUTPUT`（重试 1 次后转人工）。**禁止用正则"抠出 JSON"**——那是掩盖问题。生成建议时可 `think: true`，但 `message.thinking` 与 `message.content` 必须分开：只有 content 进 schema 校验，thinking 不入库（常含学生原文，违反 R6）。
2. **结构化输出用受约束解码**：`/api/chat` 传 `format=<JSON Schema>`，schema 与 Pydantic 模型同源生成；`rel_type`/`node_type` 一律用 enum。
3. **8B 能力边界**：单 chunk ≤400 字、单次三元组 ≤8 条、单次字段 ≤6 个；超了切小，不许加大 `num_predict`。"建议是否可执行"**不交给模型**，只走图谱确定性查询。

性能与预算：8B Q4 单 chunk 抽取 GPU(8G) 约 15–30s、CPU 约 60–150s。因此单步 90s、单条 240s、`max_steps=8`、回放 `--workers 1` 夜间批跑。超时按序降级：`num_ctx 8192→4096` → chunk `400→300 字` → `top_k 8→5`；**不许调大步数、不许换更小模型凑数**。显存预算：chat 6–7GB + embed 1.2GB，8G 卡上不要同时常驻，`OLLAMA_NUM_PARALLEL=1`，启动日志打印 `ollama ps`。

知识库与图谱的三条结构性约束（不写死会被绕过）：
① 图谱只服务五个查询——Q1 `task→能力→课程单元→课程`（24/30 判定）、Q2 `course→受影响任务`、Q3 `enterprise→岗位→任务` 连通率、Q4 冲突边、Q5 孤立/无源边；不能服务其中之一的节点边，不建。
② 节点白名单 10 类（Major/Course/CourseUnit/Post/Task/ObservationPoint/Competency/Enterprise/Rule/Doc），边白名单 8 类（OFFERS/BELONGS/REQUIRES/MAPPED_TO/PART_OF/COVERS/CONSTRAINED_BY/NOT_COVERS），禁止自由命名关系，**禁止建 Student/Feedback/Evidence 节点**（个体数据只作边 provenance）。
③ 建图与判定分离：建图只在离线 `kg-build`，运行时模型只能读图不能改图；新边默认 draft，人工审核后 active；判定 pin `kg_snapshot_id`。否则"自己建边、自己判可执行"会让 24/30 虚高且无法复现。

统一契约：`{"ok": bool, "data": ..., "error": {"code": str, "msg": str}}`；`ok=false` 时 data 必须为 null；分页 `{items,total,page,page_size}`；时间存 UTC、展示 Asia/Shanghai。错误码 26 个，每个必须有测试：`E_CONFIG_MISSING` `E_AUTH_REQUIRED` `E_AUTH_DENIED` `E_SCOPE_VIOLATION` `E_NOT_FOUND` `E_CONFLICT` `E_DUPLICATE` `E_SCHEMA_INVALID` `E_MAPPING_UNRESOLVED` `E_STALE_DATA` `E_EVIDENCE_MISSING` `E_GATE_STOPPED` `E_LLM_TIMEOUT` `E_LLM_INVALID_OUTPUT` `E_LLM_UNAVAILABLE` `E_RETENTION_BLOCKED` `E_READONLY_VIOLATION` `E_TOOL_NOT_ALLOWED` `E_HARNESS_BUDGET` `E_KB_MISS` `E_KB_STALE` `E_KB_UNVERIFIED` `E_KG_INVALID` `E_KG_NO_PATH` `E_KG_CONFLICT` `E_INTERNAL`。
