## 1. 执行摘要

客户的原话是"用 AI 整理实习反馈、发现教学改进需求"。但调研结论是：**客户以为病在"整理慢"，实际病在三处**——换岗后反馈发错人、企业说不出哪个岗位任务没做好、建议落不到具体课程。这三处不修，整理得越快，糊涂账抄得越整齐。

因此本方案不建"自动评价系统"，而建**受控辅助工作流**：把企业反馈整理成**可追溯到原文、可对应到课程与岗位任务、经人确认**的改进建议。四个部件各管一件事，互不顶替：

- **Harness**（自建，基于 FastAPI 的受控执行骨架）：工具白名单 + 两级策略 + 步数与时间预算 + 全链路 trace。它决定"能不能执行"，不决定"该不该建议"。
- **知识库（KB）**：岗位任务模板、课程—能力口径、规则版本，全部带版本与生效期，检索结果可点回原文段落。
- **知识图谱（KG）**：课程—任务—能力—岗位的实体与关系，把"建议能否落到课"从人工争辩变成一次确定性查询。
- **人工闸门**：确认、退回、停止、签发口径、否决。

技术底座固定：**Python 3.11+ / FastAPI / Ollama 本地部署 Qwen3-8B / 自建 KB 与 KG**，默认零外发，学生数据不出校。

验收不看"感觉准不准"，看三个可复算的数：**30 条建议中 ≥24 条可对应课程、任务、改进负责人；100% 可点回原文与版本；反馈完整率 54%→85%（按样本验证后）**。

## 2. 背景与问题诊断

### 2.1 现状与规模

| 项 | 现状 | 来源 |
| --- | --- | --- |
| 实习规模 | 每学期约 600 名学生 | f00 |
| 反馈完整率 | 54%，目标 85% | f00 |
| 教师负荷 | 每位教师带 30 人，每月约 10 小时整理微信/Excel/邮件 | f12 |
| 主链路 | 企业评分 → 教师回访 → 教务汇总 → 专业组评审 | f01 |
| 反馈质量 | 企业常只写"沟通能力不足"，不落到岗位任务 | f10 |
| 换岗处理 | 系统仍关联旧导师，反馈发错人，靠群聊逐个确认 | f11 |
| 系统条件 | 学籍/实习/课程三套 ID 不通；仅开放只读批量导出 | f30 / f32 |

上述数字均为**访谈口径**，基线须按样本验证后方可作为验收依据。这一点必须写进所有对外材料，否则会把估计值当结论用。

### 2.2 三处病根

| 病根 | 发生机制 | 不修的后果 |
| --- | --- | --- |
| 换岗后反馈发错人 | 学生换岗/延期后，`assignments` 仍指向旧导师；旧导师继续催填，新导师没收到提醒（f11）。同事先在群聊或个人表补说明再回系统（f14） | 双周节拍断掉；旧导师填的内容对不上新岗位任务；交接责任说不清（f23/f25） |
| 企业说不出哪个任务没做好 | 反馈模板没有岗位任务字段；历史数据该字段缺失，空值被当"没问题"（f31）；企业与学校的任务口径不一致（f51） | AI 只能把"沟通能力不足"改写成同义词，教师仍不知道该让学生改哪个动作 |
| 建议落不到课程 | 教务流程止于"专业组确认"，缺"谁把建议转成课程改进任务"的环节（f20/f01） | 24/30 无法达成；评审记录无法回灌培养方案；模型不进成绩与方案（f22） |

### 2.3 为什么先修管道，再装泵

如果先做 AI 整理，会发生四件事：输入仍是 54% 的样本（缺的部分本来就没材料）；输入仍无岗位任务字段（输出是同义改写）；仍无原文追溯与确认人（傅景不签字）；分母仍未固定（改善了也证明不了）。**先修管道，AI 整理的价值才能被单独测量。** 这是本方案把"口径、模板、换岗重关联、双周节拍、只读映射"排在 AI 整理之前的唯一理由。

### 2.4 业务门 G0–G4

| 门 | 时点 | 通过标准 | 放行人 | 不通过 |
| --- | --- | --- | --- | --- |
| G0 | 开工前 | 一页口径说明签发；两方独立复算同一数字，误差 = 0 | 顾明岚签发 · 傅景确认 | 不启动 W1，先补口径 |
| G1 | W1 | 1 家企业用现有样本试填三字段，可填比例达标、单条整理分钟未上升 | 林亦舟 + 叶书 | 减字段，不换方案 |
| G2 | W4 | 30 条历史反馈回放：≥24/30 可对应，100% 可点回原文与版本 | 傅景（不签字即不过） | 退回模板与口径，不进入试点 |
| G3 | W2–W3 | 只读导出获批；主编号/事件时间/来源/版本四项通过率 ≥90% | 秦芮 | 先修数据，整理不启动 |
| G4 | 4 周末 | 按期率、教师工时、24/30 三项同时可接受 | 顾明岚主持 · 傅景否决 · 叶书参与 | 只保留流程改进，不扩范围 |

门的顺序不能换：G2 早于 G4，是为了让"做不出来"发生在花钱之前。

## 3. 建设目标与非目标

### 3.1 目标（每条可验收）

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| O1 | 每条建议可点回原文、版本、采集时间 | 抽检 30 条，100% 可定位到 span |
| O2 | 每条建议可对应课程、岗位任务、改进负责人 | 30 条中 ≥24 条四元组齐备且图上连通 |
| O3 | 换岗/无实例/口径冲突时自动停止并转人工 | 构造 5 类用例，全部返回原因+接手人+确认时间 |
| O4 | 三项指标可被第三方复算 | 两方独立复算，误差 = 0 |
| O5 | 学生数据不出校，个体记录按企业隔离 | 抓包 + 越权测试，零外发、零跨企业命中 |

### 3.2 非目标（首期明确不做）

| 不做 | 理由 |
| --- | --- |
| 成绩/学分写回，任何外部写接口 | 模型不能决定成绩（f22）；写回接口不在范围内（f32） |
| 自动评分、能力定性、学生画像、排名 | AI 只整理事实与建议，最终评价由导师确认（f52） |
| 培养方案变更、通用审批流引擎 | 须教务委员会审批（f22），属项目边界之外 |
| 通用知识图谱平台（多模态、全网爬取、自由问答、链接预测） | 图只服务 §8.3 的五个查询，多余能力会稀释验收 |
| 自由对话式入口 | 无逐句引用的对话结论违反 f15/f45；要做放 P2 且每句强制带引用 |
| 课程改进台账、投诉工单 | 证据为零（评审频次/采纳率未采集）与 P2 定位 |
| 微服务、容器编排、消息队列、图数据库、向量数据库、LangChain | 4 周 / 12 万元 / 单机试点，引入即超支；无一项能被验收门槛要求 |
| 学期末长问卷替代方案 | 长问卷会拖到期末（f50），方向相反 |

## 4. 总体架构

### 4.1 四部件职责

| 部件 | 职责 | 不负责 |
| --- | --- | --- |
| Harness | 工具白名单、两级策略、步数/时间预算、trace、失败降级 | 不决定业务判断，只决定执行边界 |
| 知识库 KB | 组织级知识：K1 岗位任务 / K2 课程口径 / K3 规则版本；切片检索与引用 | 不判关系；不存个体数据 |
| 知识图谱 KG | 实体关系与多跳查询；可对应性判定；口径断裂量化 | 不做检索；不替代原文引用；不在线写入 |
| 人工闸门 | 确认 / 退回 / 停止 / 签发 / 否决 / 留存处置 | 不手工搬数据 |

### 4.2 分层结构

```
┌─────────────────────────────────────────────────────────────┐
│ 接入层  FastAPI（统一响应 / 全局异常 / 会话鉴权 / 依赖注入）      │
├─────────────────────────────────────────────────────────────┤
│ 应用层  ingest → mapping → extract → suggest → review → metrics │
│         全部经 Harness 调度，禁止越层直连模型或直写库            │
├─────────────────────────────────────────────────────────────┤
│ 部件层  Harness  │  KB（切片/检索/引用/快照）  │  KG（本体/查询） │
├─────────────────────────────────────────────────────────────┤
│ 模型层  LLM 适配（Ollama qwen3:8b / 受约束解码 / 降级）          │
├─────────────────────────────────────────────────────────────┤
│ 数据层  SQLAlchemy + Alembic；SQLite（开发）→ PostgreSQL（试点）  │
├─────────────────────────────────────────────────────────────┤
│ 审计层  append-only audit_logs（人操作 + 模型调用 + 策略判定）     │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 单条记录的数据流

固定 6 个业务步骤，允许提前终止，不允许加第 7 个：

| # | 步骤 | 输入 | 输出 | 失败时 |
| --- | --- | --- | --- | --- |
| 1 | `feedback.get` | record_id | 原文、渠道、周期、版本 | 不存在 → `E_NOT_FOUND` |
| 2 | `mapping.resolve` | 学生/实习 ID | 课程 ID、批次、四项校验结果 | 未映射 → `E_MAPPING_UNRESOLVED` |
| 3 | `task_template.match` + `kb.search` | 岗位、原文 | 候选任务 + 检索片段 | 无候选 → `needs_review` |
| 4 | `kg.path` | 任务 ID | ≤3 跳路径与 doc 引用 | 无路径 → `E_KG_NO_PATH` |
| 5 | `evidence.locate` | 原文引句 | span 起止 | 定位失败 → `E_EVIDENCE_MISSING` |
| 6 | `suggestion.draft` → `review.enqueue` | 上述结果 | draft 建议 + 待办 | 闸门不过 → `E_GATE_STOPPED` |

### 4.4 两种运行模式必须同构

| 模式 | 数据 | 用途 | 约束 |
| --- | --- | --- | --- |
| 在线 | 当期批次 | 教师日常使用 | 受时间预算约束，超时转人工 |
| 回放 | 30 条历史反馈 | G2 验收与回归 | 必须 pin `kb_snapshot_id` + `kg_snapshot_id` + `model_digest` |

两者跑**同一个 Harness 实现、同一套工具、同一套策略**。为回放另写一套流程，等于用另一条路径证明这条路径可行，结论无效。

## 5. 技术选型

### 5.1 选型总表

| 层 | 选型 | 版本/说明 |
| --- | --- | --- |
| 运行时 | Python | 3.11+（`requires-python = ">=3.11"`） |
| Web 框架 | FastAPI + Uvicorn | 唯一 HTTP 入口 |
| 数据校验 | Pydantic v2 | 入参、模型输出、KB 命中、图三元组统一 schema |
| ORM/迁移 | SQLAlchemy 2.x + Alembic | 迁移可回滚，开发与试点同一套 |
| 存储 | SQLite（开发）/ PostgreSQL 16（试点） | 禁止两套 schema |
| 执行骨架 | 自建 Harness | 不引第三方 Agent 框架 |
| 知识库 | 自建 KB，默认 bigram-BM25 | 可选 `bge-m3` 向量，SQLite BLOB |
| 知识图谱 | 三元组表 + 递归 CTE | 不引图数据库 |
| 模型运行时 | Ollama，`qwen3:8b`（Q4_K_M） | 本地零外发；embedding 用 `bge-m3` |
| 前端 | Jinja2 + 原生 HTML/CSS/少量 JS | 无 npm 构建链 |
| 鉴权 | 自建 Session + users/roles | 不引 OAuth/Keycloak |
| 办公文件 | openpyxl / python-docx / pypdf | 导入与语料解析 |
| 测试 | pytest + httpx TestClient | 错误码、红线、工具策略、图查询全覆盖 |
| 日志 | stdlib logging，JSON 行 | 不引 ELK/OTel |
| 调度 | 无调度器 | 刷新/建图/回放走 CLI + 系统计划任务 |

### 5.2 关键取舍

| 决策 | 放弃的方案 | 理由 |
| --- | --- | --- |
| 自建 Harness（约 600 行） | LangChain / LangGraph / AutoGen | 需要的是"不许多做"的边界，不是"能多做"的编排；第三方框架的工具注册与回调会绕过审计字段 |
| 三元组表 + 递归 CTE | Neo4j / JanusGraph | 规模 5 万节点/30 万边以内，SQLite 递归 CTE 足够；图数据库带来运维与授权成本，却换不到验收门槛 |
| bigram-BM25 默认，向量可选 | 一上来就上向量库 | 中文词表未定、语料未到；bigram 零依赖、可解释、命中即原文；向量作为增强而非前提 |
| Ollama + Qwen3-8B 本地 | 云端大模型 API | f40/f41/R6 要求个体记录限访问、最小化；本地推理让"数据不出校"从承诺变成事实 |
| Jinja2 服务端渲染 | React/Vue 单页 | 4 周交付、6 类角色、以表单与队列为主；构建链只会增加交付风险 |
| SQLite → PostgreSQL 同迁移 | 直接上 PostgreSQL | 开发环境零部署；同一套 Alembic 迁移保证不漂移 |

### 5.3 为什么必须是 FastAPI + Python 3.11+

- FastAPI 的 `response_model` + 全局异常处理器，正好承载"统一响应结构"与"任何异常不得裸奔成 500"两条硬要求。
- 依赖注入统一出 `Principal`，是"作用域过滤落在查询层"的实现位置。
- Python 3.11+ 提供 `StrEnum`/`Self`/`datetime.UTC`/`tomllib`，状态机与代码都用得上；不写降级兼容代码，避免为兼容 3.8 引入类型 hack。
- 团队既有代码（`知行-实习反馈-业务机会/` 下的 `build_baseline_workbook.py`、`verify_workbook.py`）均为 Python，复用验证脚本的写法可以省一轮沟通。

## 6. 本地模型方案（Ollama + Qwen3-8B）

### 6.1 部署形态与硬件预算

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 运行时 | Ollama ≥0.9 | `think` 参数从 0.9 起支持 |
| 监听 | `127.0.0.1:11434` | 仅本机，不对外暴露 |
| 对话模型 | `qwen3:8b`（Q4_K_M，约 5.2GB） | 抽取、归并、起草 |
| 向量模型 | `bge-m3`（约 1.2GB，1024 维） | `qwen3:8b` 不是 embedding 模型，不能替代 |
| 并发 | `OLLAMA_NUM_PARALLEL=1` | 8G 显存下并发会让模型重复加载 |
| 显存 | 对话 6–7GB（含 8k 上下文）+ 向量 1.2GB | 8G 卡上不要同时常驻 |

### 6.2 配置清单

```yaml
llm:
  provider: ollama                 # 默认；openai_compat 仅在获批后启用
  base_url: "http://127.0.0.1:11434"
  chat_model: "qwen3:8b"
  embed_model: "bge-m3"
  num_ctx: 8192                    # Ollama 默认 4096，长反馈会截断
  num_predict: 1024
  temperature: 0
  top_p: 0.9
  seed: 42
  keep_alive: "30m"
  think: false                     # 抽取任务必须关
  allow_remote: false              # 默认零外发
  model_digest_pin: "<首次 pull 后回填>"
  timeout_ms: 90000
```

### 6.3 thinking 必须关闭

Qwen3 是混合推理模型，默认先输出"好的，我来分析…"，`format` 约束挡不住思维链文本，JSON 解析必挂。三处同时处理：

1. 请求体 `think: false`；
2. prompt 末尾追加 `/no_think`；
3. 解析层**不做修复**——输出不以 `{` 开头，直接判 `E_LLM_INVALID_OUTPUT`，重试 1 次后转人工。禁止用正则"抠出 JSON"，那会把脏数据放进库。

生成改进建议时可 `think: true` 提升质量，但 `message.thinking` 与 `message.content` 必须分开：只有 `content` 进 schema 校验，`thinking` 不入库（思维链常复述学生原文，入库即破 R6），最多存 hash 供排查。

### 6.4 8B 的能力边界

| 约束 | 取值 | 原因 |
| --- | --- | --- |
| 单 chunk 长度 | ≤400 字 | 超长时后半段字段缺失 |
| 单次三元组 | ≤8 条 | 超了会漏、会串行 |
| 单次输出字段 | ≤6 个 | 字段越多越容易漏 `required` |
| 是否可判定"建议可执行" | **否** | 8B 裁决不稳定；该判断交给 §8.3 的确定性图查询 |

判定权从模型移到图查询，不只是合规考虑，也是能力边界：8B 在 30 条样本上的裁决一致性达不到验收要求。

### 6.5 性能预算

| 场景 | GPU（8G） | CPU | 处置 |
| --- | --- | --- | --- |
| 单 chunk 抽取（输出 400–800 tok） | 15–30s | 60–150s | 单步超时 90s |
| 单条记录（6 步） | 1–2 分钟 | 3–8 分钟 | 单条预算 240s |
| 30 条回放 | 0.5–1 小时 | 3–6 小时 | `--workers 1`，夜间批跑 |

超时按顺序降级：`num_ctx 8192→4096` → chunk `400→300 字` → `top_k 8→5`。**不许调大步数、不许换更小的模型凑数**——那会让 30 条回放的结论失去意义。

### 6.6 版本固定

`qwen3:8b` 是滚动 tag，不同时间 pull 的权重可能不同。首次拉取后把 digest 写入 `llm.model_digest_pin`；启动时比对，不一致只告警不阻断，但必须写审计；回放强制用 pin 的 digest，否则结论不可复算。

### 6.7 故障模式与处置

| 现象 | 原因 | 处置（按序，不跳步） |
| --- | --- | --- |
| 输出以"好的/我来分析"开头 | thinking 未关 | `think:false` + `/no_think`；重试 1 次后转人工 |
| `format` 生效但字段缺失 | schema 太宽 | 全字段 `required`、`additionalProperties:false`；chunk 降到 300 字 |
| 三元组只抽到 2–3 条 | `num_predict` 截断 | 切小 chunk 分批；不要加大 `num_predict` |
| 同输入两次结果不同 | think 开着 / seed 未固定 | 关 think、固定 seed 与温度 0 |
| OOM、模型反复换出 | chat 与 embed 同时常驻 | `NUM_PARALLEL=1`、串行、embed 降 CPU |
| 长文本后半段丢失 | `num_ctx` 用了默认 4096 | 显式 8192；chunk ≤400 字 |
| 全角标点导致解析失败 | 模型未转义 | 严格 `json.loads`，不修复、不猜，转人工 |
| Ollama 未启动 | 服务未运行 | `E_LLM_UNAVAILABLE`；应用照常启动，`/healthz` 报 `llm=down`，抽取转人工 |

## 7. 知识库设计

### 7.1 三类知识

| 编号 | 知识 | 来源 | 形态 | 审核 |
| --- | --- | --- | --- | --- |
| K1 | 岗位任务模板（岗位 → 任务 → 行为观察点） | 岗位说明书；林亦舟/叶书核定 | 结构化表 + 版本 | 林亦舟 + 叶书 |
| K2 | 课程—任务—能力口径映射 | 培养方案、课程标准 | 文档切片 + 映射 | 顾明岚 + 傅景 |
| K3 | 制度、规则、口径卡 C1–C4 | 访谈确认的规则文本 | 版本化文本 | 顾明岚签发 |

**不入库**：学生个体评价、行为实例原文、跨企业资料、口令、家庭背景/性别等敏感属性。

### 7.2 文档生命周期

`draft → active → retired`。只有 `active` 可被检索；`retired` 保留不命中；版本只增不改；每次变更写审计（谁、改了什么版本、为什么）。

### 7.3 切片与索引

- 按标题层级切，单片 200–400 字，重叠 15%；表格按行切；
- 每片保留 `page/paragraph` 定位，供前端"点开原文对应段落"；
- 索引：字符 bigram 倒排（默认）/ `bge-m3` 向量（可选）/ RRF 融合（hybrid）。

### 7.4 引用强制

涉及课程、岗位任务、口径的表述必须带 `kb_ref = {doc_id, version, chunk_id, span}`：

- 版本过期或无 `effective_from` → 标"仅供参考"，不得作依据（`E_KB_STALE`）；
- 未命中 → 字段 `null` + `needs_review`，不许用模型常识补（`E_KB_MISS`）；
- 前端点 `kb_ref` 打不开对应段落，视为引用造假。

### 7.5 检索评测

30 条回放样本人工标注"应命中的任务模板/课程条目"，计算 `Recall@5`（门槛 ≥0.80）、`MRR@5`、引用正确率（抽检 30 条，须 100% 可定位）。

## 8. 知识图谱设计

### 8.1 为什么需要图

f01/f42 要求"建议落到具体课程"，本质是 `岗位任务 → 能力项 → 课程单元 → 课程` 的多跳关系。用字段硬堆需要四层外键加人工维护；用图查询，一次可达性判断即可给出"可执行/不可执行 + 路径 + 依据"。同时把 f51 的"企业与学校口径对不齐"变成可计算数字。

### 8.2 本体：节点与边白名单

**节点（10 类）**：`Major`（专业）、`Course`（课程）、`CourseUnit`（课程单元：章/节/实训项目）、`Post`（岗位）、`Task`（岗位任务）、`ObservationPoint`（行为观察点）、`Competency`（能力项）、`Enterprise`（企业）、`Rule`（规则/口径）、`Doc`（来源文档）。

**边（8 类）**：`OFFERS`（企业→岗位）、`BELONGS`（任务→岗位）、`REQUIRES`（任务→能力）、`MAPPED_TO`（课程单元→能力）、`PART_OF`（课程单元→课程）、`COVERS`（课程→任务）、`CONSTRAINED_BY`（任务/指标→规则）、`NOT_COVERS`（课程→任务，冲突用）。

**禁止建节点**：`Student`、`Feedback`、`Evidence`、`Mentor`。个体数据只作为边的 `provenance` 引用存在。若不写死这条，f40 的"不向其他企业公开个体记录"必然被图绕过——图谱天生倾向于把一切连起来。

### 8.3 五个查询（除此之外不建图）

| 编号 | 查询 | 用途 | 证据 |
| --- | --- | --- | --- |
| Q1 | `task → 能力 → 课程单元 → 课程`（≤3 跳） | 24/30 的可执行性判定 | f01 / f42 |
| Q2 | `course → 受影响任务/能力`（反向） | 课程改进影响面 | f01 / f55 |
| Q3 | `enterprise → 岗位 → 任务` 的可连通比例 | 口径断裂量化 | f51 |
| Q4 | 同一 `(from,to)` 同时存在 `COVERS` 与 `NOT_COVERS` | 口径矛盾待裁决 | f24 / f44 |
| Q5 | 孤立节点、无 provenance 边 | 图质量告警 | — |

任何节点或边，若不能服务上述五个查询之一，不建。

### 8.4 构建流水线

```
kg-build --docs <ids> --snapshot <id>
  1 extract     # 逐 chunk 调 Ollama，format=JSONSchema，抽候选三元组
  2 normalize   # 别名表归一；相似度超阈值只进"待合并"队列，不自动合并
  3 validate    # 类型白名单、端点存在、无自环、无重复边（upsert）、provenance 必填
  4 review      # 新边 draft → 人工审核 → active；审核人按 K1/K2/K3 分区
  5 publish     # 生成 kg_snapshot（节点数、边数、hash）
```

归一**不自动合并**：合并错会污染整张图且难以回溯，相似度高只产出候选，动作写审计。

### 8.5 存储与查询

表：`kg_nodes`、`kg_edges`、`kg_aliases`、`kg_snapshots`、`kg_queries`、`kg_conflicts`。路径查询用递归 CTE，参数全部绑定：

```sql
WITH RECURSIVE reach(node_id, depth, edge_ids) AS (
  SELECT :task_id, 0, json_array()
  UNION ALL
  SELECT e.to_id, r.depth + 1, json_insert(r.edge_ids, '$[#]', e.edge_id)
  FROM kg_edges e
  JOIN reach r ON e.from_id = r.node_id
  WHERE e.status = 'active' AND r.depth < :max_hops
)
SELECT node_id, depth, edge_ids FROM reach
WHERE node_id IN (SELECT node_id FROM kg_nodes WHERE type = 'Course');
```

规模上限：节点 5 万、边 30 万；热点子图做进程内 LRU 缓存；超过上限再评估图数据库。

### 8.6 质量门槛（M2 必过）

| 指标 | 门槛 |
| --- | --- |
| 边 provenance 覆盖率 | 100% |
| 孤立节点占比 | ≤5% |
| Q1 路径覆盖率（可识别任务能找到 ≤3 跳到课程） | ≥80% |
| 未裁决冲突边 | 0 |
| 节点/边类型越界 | 0 |

### 8.7 防自证循环的三条机制

1. **建图与判定分离**：建图只在离线 `kg-build`，模型运行时不能新增节点或边。
2. **只用 `active` 边、只用已发布快照**：判定时 pin `kg_snapshot_id`。
3. **新边必须人工审核**：抽取出的边默认 `draft`，审核人按知识分区指定。

否则会出现"模型自己建边、自己判可执行"的循环，24/30 会虚高且无法复现。

## 9. Harness 设计

### 9.1 职责边界

Harness 回答一个问题：**这次能给模型多大权限、跑多久、留什么痕。** 它不回答"该不该给建议"。

### 9.2 工具白名单

| 工具 | 类别 | 作用 | 副作用 |
| --- | --- | --- | --- |
| `kb.search` | 读 | 检索知识片段 | 记 `kb_queries` |
| `kg.path` | 读 | 多跳路径查询 | 记 `kg_queries` |
| `kg.neighbors` | 读 | 邻域子图 | 记 `kg_queries` |
| `feedback.get` | 读 | 取原文与版本 | 审计 |
| `mapping.resolve` | 读 | 三套 ID 映射与校验 | 审计 |
| `task_template.match` | 读 | 候选任务匹配 | — |
| `evidence.locate` | 读 | 引句定位到 span | — |
| `suggestion.draft` | 写(draft) | 落库草稿 | 仅 draft |
| `review.enqueue` | 写(queue) | 建人工待办 | 建待办 |
| `gate.check` | 判定 | 停止条件判定 | 审计 |

禁止注册：修改原文、改 KB/KG、外部写请求、任何 grade/score 字段、任何 approve、跨企业查询。调用即 `E_TOOL_NOT_ALLOWED`。

### 9.3 两级策略

- **L1 before_tool**：参数合法性、作用域、`stale` 拦截、只读白名单、KB/KG 分区。
- **L2 before_commit**：R2 字段白名单 → R3 至少 1 个 `evidence_ref` → R4 空值必须 `needs_review` → R11 `kb_ref` → R13 `kg_ref`（路径边全 `active`）→ f44 五类停止条件。

任一级失败即不落库，返回 `E_GATE_STOPPED`，并强制带 `{reason, assignee, confirm_at}` 三字段。

### 9.4 预算与降级

`max_steps=8`、单步 90s、单条 240s、token 8000/条、重试 1 次（仅超时/输出不合法）。超限 → `E_HARNESS_BUDGET` + 转人工，不抛 500、不静默截断。回放沿用同一预算。

### 9.5 trace 与重建

每步落 `audit_logs(object_type='harness_step')`：`run_id, step_no, tool, args_hash, result_hash, latency_ms, model, model_digest, prompt_version, kb_snapshot_id, kg_snapshot_id, policy_result`。

给定 `run_id` 必须能重建全流程，满足 f45"审核日志能重建当次处理"。

| 学生（P2） | 本人记录 | 申请更正 | 看他人 |

实现：`Principal{user_id, role, enterprise_id, batch_scope}` 由依赖注入统一产出；作用域过滤在 SQL where 与 KB/KG 分区过滤；默认拒绝；越权写审计。

### 12.2 数据分级

| 级别 | 内容 | 处置 |
| --- | --- | --- |
| L1 | 聚合指标、口径卡 | 可导出、可上会 |
| L2 | 组织级知识（任务模板、课程口径） | 登录可读，按专业/企业分区 |
| L3 | 学生个体评价与原文 | 限角色、限企业；审计每次访问 |
| L4 | 密钥、口令、身份证、家庭背景 | 禁止入库；日志脱敏 |

### 12.3 脱敏与送模

- 默认零外发（本地模型）；
- 若获批外发，先脱敏（姓名/学号/企业名 → 代号），每次外发写审计；
- `thinking` 内容不入库；
- 日志只记 hash 与定位，不记完整正文。

### 12.4 留存与删除

`retention_days=90`（仅限本轮合成试点，真实期限另行核实）。到期生成待删除/待归档清单，须教学质量负责人角色确认后执行；先删正文，保留审计摘要。

| 形态 | 学院内网单机；不容器化（4 周试点） |
| OS | Windows 10/11 或 Linux（脚本两套） |
| 端口 | FastAPI 8000；Ollama 11434（仅本机） |
| 数据库 | 开发 SQLite；试点 PostgreSQL 16 |
| 备份 | 每日 `pg_dump` + `kb_snapshots`/`kg_snapshots` 目录增量 |

### 14.2 安装与启动

```bash
# 1 模型
ollama pull qwen3:8b
ollama pull bge-m3
ollama run qwen3:8b "/no_think 只回复 OK"
ollama show qwen3:8b          # 记录 digest 回填 config.yaml

# 2 依赖与迁移
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
alembic upgrade head

# 3 知识库与图谱
python -m app.cli kb-ingest --dir ./corpus
python -m app.cli kg-build --docs all --snapshot s001

# 4 启动
uvicorn app.main:app --host 127.0.0.1 --port 8000
curl http://127.0.0.1:8000/healthz
```

### 14.3 健康检查与降级

`/healthz` 返回 `{db, llm, kb, kg}` 四态。任一 down：应用照常启动，相关能力降级到人工队列，返回 `ok:false` 而非 500（f35）。

### 14.4 监控与回放作业

- 指标：请求量、闸门触发率、模型 p95 延迟、`E_LLM_*` 计数、KB 命中率、图路径失败率；
- 回放：`python -m app.cli replay --cases 30 --kb-snapshot s001 --kg-snapshot g001 --workers 1`，夜间计划任务；产物含可追溯率、KB 命中率、路径覆盖率、24/30 判定与逐条原因。

## 16. 测试策略

### 16.1 分层

| 层 | 内容 | 工具 |
| --- | --- | --- |
| 单元 | 校验器、状态机、策略、预算、归一 | pytest |
| 契约 | 错误码、响应结构、分页、时间格式 | pytest + schema 快照 |

| 红线 | R1–R13 各一条 | `check_readonly.py` + pytest |
| 回放 | 30 条历史样本 | `replay` CLI |

### 16.2 指标复算口径

| 指标 | 分子 | 分母 | 时间窗 |
| --- | --- | --- | --- |
| 反馈完整率 | 提交且通过校验的反馈人次 | 应提交的"学生×双周"人次 | 学期，按双周分段 |
| 建议可执行率 | 课程/任务/负责人齐备且图上连通的建议数 | 专业组审阅总数 | 评审周期 |
| 教师整理工时 | 归拢+核对+回访时长（四类拆分） | 所带学生数或反馈条数 | 每月 |

分母、周期、排除规则由业务负责人固定并签发，代码不得硬编码。

### 16.3 回放设计

30 条历史反馈必须包含：换岗、无行为实例、口径冲突、字段缺失各若干；必须使用历史数据而非新造样本（新样本会掩盖"历史缺岗位任务字段"这一事实）。

| 风险 | 触发条件 | 影响 | 对策 | 责任 |

| 引用造假 | 前端打不开段落 | 审计失效 | 引用可点击校验进 M3 门槛 | 开发 |
| 教师不认 | 确认耗时 > 整理耗时 | 试点失败 | 工时四类拆分对比；G4 用数据决策 | 林亦舟 |
